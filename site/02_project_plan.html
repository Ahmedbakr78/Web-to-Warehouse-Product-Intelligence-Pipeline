1. Planning approach

The plan follows a requirements → design → build → verify → document sequence, with two deliberate parallel tracks:

  • Data track — warehouse schema, cleaning, dedupe, quality, reconciliation. This is the

academically interesting part and must be right before anything is presented.

  • Serving track — REST API and dashboard. It consumes only the analytical views, so it can start

as soon as db/views.sql is stable (end of W5).

Two hard constraints shaped the plan:

  • The warehouse must be demonstrable offline (local_demo), so no external dependency can block a

sprint demonstration.

  • Cross-dialect verification requires both databases, so W1 includes the Docker Compose bring-up.

7.1 Change control

After milestone M2 (Design frozen) the following rules apply:

  • Any schema change requires a design note in docs/09_database_design.md explaining the impact on

the ERD, the views and the API.

  • Any new endpoint requires an entry in docs/14_api_documentation.md and a check in

scripts/api_smoke.py.

  • Any new source requires a terms_allowed justification in docs/01_project_proposal.md §8.2.
