Every number in this document was measured on the running system, not estimated. The command that produced each figure is given with it, so any claim here can be re-derived and falsified.

Purpose

Two questions decide whether a pipeline is production-shaped or a demo:

  • Does it stay fast as the warehouse grows? A dashboard that reads 80,000

rows in 300 ms is fine. The same code over 5,000,000 rows is not, unless the access paths are indexed for the growth.

  • Does it stay honest as it grows? More data means more chances to be

wrong. The guarantee that every row was really observed has to survive the growth, not just the demo.

This document records the measured behaviour, the decisions that produce it, and the plan for the next order of magnitude.

The three decisions that make it scale

1. The KPI payload stopped counting what it does not publish

kpi_summary used to run SELECT COUNT(*) against sixteen tables to build a counts object, of which the dashboard read exactly one. Counting fact_price_snapshot alone was 13 ms at 83,000 rows and would be 800 ms at 5,000,000 — spent on a number the screen never shows.

The count set is now explicit:

#: The subset the KPI payload carries. Counting every table on every dashboard
#: load is wasted work: a COUNT(*) over a half-million-row fact table is the
#: single most expensive part of the request, and the dashboard never shows it.
KPI_COUNTED_TABLES: tuple[str, ...] = (
    "dim_product",
    "fact_price_snapshot",
)

The full set stays available on the health endpoint and the pipeline totals report, where it belongs. Measured effect: 290 ms → 150 ms for the dashboard query.

2. The windowed timestamps carry an index

Every headline number is a window: "price changes in the last 30 days", "observations in the last 7 days". Those queries filter on captured_at (facts) and detected_at (change tables) — and neither column had an index, so the planner sequential-scanned the whole fact table on every dashboard load.

The plan before and after, from the live database:

-- Before: 83,306 rows scanned, 71 ms
EXPLAIN (ANALYZE) SELECT COUNT(DISTINCT product_id) FROM fact_price_snapshot
WHERE captured_at >= now() - interval '30 days';

--  Aggregate (actual time=24.092..24.095 rows=1)
--    ->  Seq Scan on fact_price_snapshot (actual time=0.013..13.608 rows=47403)

-- After: an index-only scan over the window
--    ->  Index Only Scan using ix_fact_price_captured_product
--          Index Cond: (captured_at >= (now() - '1 day'::interval))

Three indexes fix it:

Index Table Columns Serves
ix_fact_price_captured_product fact_price_snapshot (captured_at, product_id) the window filter and the distinct-product count in one index-only scan
ix_chg_event_detected chg_product_event (detected_at) the lifecycle counters
ix_chg_price_detected chg_price_change (detected_at) the price-change counters and the top-movers window

They are created concurrently on PostgreSQL, so a large table is not locked during the build:

CREATE INDEX CONCURRENTLY IF NOT EXISTS "ix_fact_price_captured_product"
  ON "fact_price_snapshot" ("captured_at", "product_id");

A sequential scan is still chosen when the window covers most of the table — which is correct, and cheaper. The index pays off exactly when the data outgrows the window, which is the case that matters.

3. The fact grain is append-only

The fact grain is product x source x captured_at, enforced by a unique constraint. Re-observing a product appends a row rather than updating one, so the write path never contends and the read path is a pure scan of a time-ordered structure.

flowchart LR
    A["Product observed<br/>again"] --> B["New fact row<br/>captured_at = now"]
    B --> C["Unique constraint<br/>product x source x run"]
    C --> D["Append-only history"]
    D --> E["Price change detected<br/>vs the previous row"]
    E --> F["Windowed queries<br/>read the newest N"]

That is why the change tables are derived rather than updated: a price change is a comparison between two adjacent rows, so it is computed once, at load time, and never recomputed.

Capacity planning

The pipeline's growth is not linear — it is runs x sources x records per source, and the last term is set by the upstream, not by us.

Dimension Today At 10x At 100x
Runs per day 3 3 3
Sources per run 20 20 20
Records per source per run ~40 ~400 ~4,000
Observations per day ~2,400 ~24,000 ~240,000
Observations per year ~880,000 ~8.8 M ~88 M
Fact table size 110 MB ~1.1 GB ~11 GB
Database total 278 MB ~2.8 GB ~28 GB

The three levers, in the order a team would reach for them:

  • Records per source per run — --limit. The cheapest lever, and the one

the upstreams constrain anyway. A source that publishes 4,000 records can only be collected 4,000 times a run.

  • Runs per day — the Airflow schedule. More runs means a denser history,

not more products, so this lever buys resolution rather than breadth.

  • Sources — adding an upstream multiplies the product count. The registry

is 35 adapters today.

What breaks first, and what it costs

Scale Bottleneck Symptom Fix
1 M observations None Dashboard ~300 ms —
10 M COUNT(DISTINCT product_id) over a wide window KPI query ~1.5 s Narrow the window, or pre-aggregate into agg_category_daily
10 M stg_raw_observation grows without bound Load stage slows Partition by month, or truncate staging after a successful load
50 M fact_price_snapshot index depth Write amplification Partition by captured_at range
Any Upstream rate limits Runs take hours More sources, not bigger limits — the limits are the sources' rules

The pre-aggregate that already exists

agg_category_daily (category x date) is rebuilt on every load from the facts. It is the escape hatch for the first real bottleneck: any question of the form "how did category X move in the window" can be answered from 1,596 rows instead of scanning 83,000 facts.

-- The category answer, straight from the aggregate.
SELECT category_name, observation_count, avg_price_usd, price_stddev
FROM vw_category_price_index
WHERE full_date >= current_date - 30
ORDER BY observation_count DESC;

The cost side: politeness is a budget

The slowest thing in the system is not the database. It is the wait for an upstream that says so.

Source Declared limit Effect on a 20-source run
openfoodfacts_prices 10 req/min the run cannot outrun ~6 s per request
coingecko_markets 10 req/min and robots.txt refuses /coins/markets entirely
kraken_tickers 20 req/min ~3 s per request
cheapshark_deals 20 req/min the most productive source per request
dummyjson_products 60 req/min fast, but synthetic — never auto-selected

A full 20-source run takes 3 m 55 s on a cold cache and ~1 m 40 s with the response cache warm. The difference is the rate limiter doing its job.

This is a deliberate trade: the pipeline would be 20x faster if it ignored the declared limits, and it would also be the reason nobody runs it twice.

Honest limits

Three things this system does not do, stated plainly so nobody has to discover them:

  • It does not stream. Data is collected in bounded batches, not

continuously. The Airflow DAG runs on a schedule; there is no always-on listener. A source that changes between runs is observed at the next run.

  • It does not guarantee overlap between sources. The three book upstreams

sample their catalogues independently, so the same title can appear in one and not another. The cross-source overlap analytics therefore report zero on this warehouse — which is a true finding, not a broken query. A test injects an overlapping product to prove the grouping works.

  • It does not scale beyond one node's write throughput. The loader is

single-writer by design. Sharding the load stage across workers is the natural next step, and the staging table's run_id column is already the right partitioning key.

How to re-measure all of this

Every number above is reproducible:

# Response times through the API
TOKEN=$(curl -s -X POST localhost:8000/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@example.com","password":"Admin@12345"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')
for ep in health "analytics/kpi?days=30" "products?page_size=25" "sources"; do
  curl -s -o /dev/null -w "%{time_total}s  $ep\n" \
    -H "Authorization: Bearer $TOKEN" "http://localhost:8000/api/v1/$ep"
done

# In-process query cost
.venv/bin/python - <<'PY'
import time
from app.core.db import session_scope
from app.analytics.service import kpi_summary, daily_trend
with session_scope() as s:
    for name, fn in (("kpi_summary", lambda: kpi_summary(s, days=30)),
                     ("daily_trend", lambda: daily_trend(s, days=90))):
        fn()
        t0 = time.perf_counter()
        for _ in range(5): fn()
        print(f"{name:16} {(time.perf_counter()-t0)/5*1000:7.1f} ms")
PY
