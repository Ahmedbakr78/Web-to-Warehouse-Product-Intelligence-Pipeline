The pipeline

Seven stages from retrieval to insight

Every stage is idempotent, timed and auditable. A failing source never kills a run, and each run writes a single row of counters, timings and quality results.

1→

Retrieve

robots.txt gate (RFC 9309), token-bucket rate limits, circuit breaker, response cache, per-request audit.

2→

Clean

29-step cleaner: names, categories, prices in 18+ currencies, offline FX to USD, ratings, availability.

3→

Dedupe

Fingerprints plus Levenshtein, Jaro-Winkler, token-set and trigram similarity at a 0.90 threshold.

4→

Load

Staged, idempotent loads into 5 dimensions and 5 fact/change tables on PostgreSQL or MySQL.

5→

Detect

Price changes with magnitude bands, new and removed products, category changes and drift.

6→

Validate

12 data-quality rules across six dimensions produce a 0–100 score and a blocking gate.

7

Serve

FastAPI (110 operations) and a React 19 dashboard over 20 views, orchestrated daily by Airflow.

Data model

A Kimball star schema that runs on two databases

One SQLAlchemy 2.0 model set targets PostgreSQL 16 and MySQL 8.4 with identical DDL and analytics, verified by cross-dialect CI jobs.

Dimensions & facts

  • dim_product — fingerprints, match strategy and score, first/last seen
  • dim_category — normalised taxonomy with hierarchy paths
  • dim_source / dim_date / dim_currency — conformed axes
  • fact_price_snapshot — every observation, keyed by product and run
  • chg_price_change / chg_product_event — the change feed
  • fact_catalog_snapshot — internal SKU versus market matching

20 analytical views

  • vw_product_current / vw_price_history — current state and full trajectories
  • vw_price_changes / vw_top_movers — movement with significance bands
  • vw_new_products / vw_removed_products — lifecycle
  • vw_category_price_index / vw_brand_summary — market structure
  • vw_source_coverage / vw_http_audit — compliance evidence
  • vw_quality_latest / vw_daily_kpis — operational health
Data quality & compliance

Trust is engineered, not assumed

12 rules, 6 dimensions

Completeness, validity, consistency, uniqueness, timeliness and accuracy. Each rule records an observed value, an expectation, a pass rate and a human-readable message.

Compliance by construction

robots.txt is parsed and honoured per request, sources are terms-allow-listed, rate limits and crawl delays are enforced, and every outbound call is written to an HTTP audit log.

Scored and gated

Each run produces a 0–100 quality score. Only critical failures stop the Airflow DAG, so a single anomalous rule never silently blocks the pipeline.

API

110 documented operations, two query surfaces

FastAPI with OpenAPI 3.1, consistent error envelopes, pagination, facets, GZip, request timing headers, rate limiting, JWT rotation, API keys and three-role RBAC.

Read-only query lab

Run SELECT, WITH and EXPLAIN over all 20 views. Writes and multi-statement payloads are rejected before execution.

curl -H "Authorization: Bearer $TOKEN" \
  "http://localhost:8000/api/v1/analytics/kpi?days=30"

curl -X POST http://localhost:8000/api/v1/queries/execute \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"sql":"SELECT category_name, COUNT(*) n
       FROM vw_product_current GROUP BY 1"}'

Aggregate builder

Compose group-by, six aggregate functions and fifteen operators over 11 entities. Identifiers come from a server-side whitelist and values are bind parameters, so injection is impossible.

curl -X POST http://localhost:8000/api/v1/builder/query \
  -H "Authorization: Bearer $TOKEN" \
  -d '{"entity":"products",
       "group_by":["category_name"],
       "aggregates":[{"function":"count"},
                     {"function":"avg","column":"price_usd","alias":"avg_price"}],
       "sort":[{"column":"avg_price","direction":"desc"}]}'

Quick start

From clone to dashboard in three commands

git clone <this-repository> web-to-warehouse && cd web-to-warehouse
cp .env.example .env

# Option A - the full Docker stack (API, PostgreSQL, MySQL, Airflow, dashboard)
make up            # start every service
make bootstrap     # create the 23 tables and 20 views
make demo-postgres # load a realistic demo dataset

# Option B - local virtualenv for the backend, npm for the frontend
make install && make frontend-install
make serve         # API on :8000 (docs at /docs)
make frontend-dev  # dashboard on :5173
