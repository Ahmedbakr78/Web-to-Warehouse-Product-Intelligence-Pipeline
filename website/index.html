The pipeline

Nine stages from retrieval to insight

Every stage is idempotent, timed and auditable. A failing source never kills a run, and each run writes a single row of counters, timings and quality results.

1

Extract

robots.txt gate (RFC 9309), rate limits, circuit breaker, ETag revalidation, per-request audit.

2

Stage

Raw payloads land resumably with validity flags and reject reasons.

3

Transform

29-step cleaner: names, categories, 18+ currencies to USD, ratings, availability.

4

Resolve

Fingerprints plus 4-signal fuzzy matching at a 0.90 threshold.

5

Load

Idempotent upserts into 5 dimensions; append-only price snapshots.

6

Detect

Price changes with magnitude bands, new/removed products, category drift.

7

Aggregate

Per-category daily rollups, global and per-source.

8

Reconcile

Internal catalog SKUs matched to market listings with price gaps.

9

Quality

12 rules across six dimensions; weighted 0–100 score persisted per run.

The data journey

One product, ten steps, from a URL to a chart

Every step below is a real function in app/etl/pipeline.py, app/etl/loader.py and app/ingestion/. The same code path runs from the CLI, from a REST trigger and from the Airflow DAG — there is no separate "demo" path.

1

Robots decision

The transport asks the per-host robots cache before a socket is opened. A disallowed path raises ComplianceError and the attempt is still logged, with the rule that blocked it.

app/ingestion/http_client.py · app/ingestion/robots.py
2

Raw payload

Every adapter is a generator. It yields RawProduct objects that carry the upstream values exactly as published, with a SHA-256 content hash and the fetch timestamp.

app/ingestion/base.py · app/ingestion/sources/
3

Staging

Rows land in stg_raw_observation with the payload hash, the HTTP status, a validity flag and a reject reason — so a half-failed run stays inspectable.

app/etl/loader.py · stage()
4

Cleaning

The 29-step cleaner strips promo prefixes and suffixes, normalises the name and brand, resolves 111 category synonyms into a hierarchy path, parses locale-aware prices, applies the FX rate, rescales the rating to 0–5 and maps availability onto five values.

app/ingestion/cleaning.py · transform_product()
5

Dedupe

A three-stage cascade: fingerprint exact, then normalised-name equality, then a blended fuzzy score over four signals — Jaro-Winkler, token-set, trigram and digit signature — above the 0.90 threshold. A blocking key keeps the candidate set small.

app/ingestion/dedupe.py · DedupeEngine.find_match()
6

Load

dim_product merges on natural keys; fact_price_snapshot appends one row per product per source per run, storing the FX rate actually used so history can never be silently restated.

app/etl/loader.py · upsert_product() / insert_snapshot()
7

Change detection

The previous snapshot is pre-loaded in one ordered query, then the difference is written: absolute and percentage move with a magnitude band to chg_price_change, and new, recurring, removed and category_changed events to chg_product_event.

app/etl/loader.py · preload_latest() / detect_removed()
8

DQ gate

Twelve rules across six dimensions evaluate the run. Each verdict — observed value, expectation, pass rate and a readable message — is stored against (run_id, rule_code) and the run gets a severity-weighted 0–100 score. Only critical failures can block it.

app/etl/dq.py · dq_rule_result

Architecture

Two paths through one system

The read path and the write path meet in a single place: the SQLAlchemy 2.0 model set that targets PostgreSQL 16 and MySQL 8.4 with identical DDL. Both diagrams are hand-written SVG — no image, no script, no external dependency.

Request path — a browser asking a question

Nginx serves the built SPA and proxies /api/ to the FastAPI container, so the browser only ever talks to one origin. FastAPI resolves every query through the SQLAlchemy 2.0 session and the ORM model set; the same statements are emitted for PostgreSQL and for MySQL.

Pipeline path — a scheduler filling the warehouse

The DAG in dags/product_intelligence_pipeline.py schedules the run, guards the source set, fires the same nine stages the CLI runs, and branches to skip notification when nothing changed. Every outbound call is written to ingestion_http_log — including the ones robots.txt refused.

Ingestion

35 source modules, 34 registered adapters, one compliance gate

Every adapter — JSON APIs, two HTML scrapers and one offline fallback — passes the same robots.txt check, rate limiter, circuit breaker and audit log. Each one also declares how much its records can be trusted as market data, so a bare pipeline run can never mix a mock storefront's invented catalogue into the warehouse.

Provenance

Every row is provably observed, not generated

A warehouse that mixes a mock API's invented catalogue with Open Library's real records produces a report that looks authoritative and is entirely fictional. Three independent mechanisms make that impossible here — and all three are checkable from SQL.

1 · Declaration

Every source class declares a trust level, and the default is the strict one:

  • real — observed market records
  • sandbox — a published test corpus
  • synthetic — generated in-process

2 · Selection

A run that is not told explicitly what to collect only ever selects real sources. Anything below must be named by code (--sources books_to_scrape), and the scheduled Airflow DAG inherits the same rule.

  • Enforced by a test, not by convention
  • New sources are safe until declared otherwise

3 · Proof

Every request is logged with the robots.txt decision that permitted it, and a purge sweep removes and reports anything below real.

  • 2,152 allowed · 93 refused before the socket opened
  • purge-untrusted --dry-run to audit

Verify any deployed instance in four queries:

SELECT COUNT(*) FROM fact_price_snapshot WHERE source_code = 'local_demo';      -- 0
SELECT COUNT(*) FROM fact_price_snapshot WHERE product_url LIKE '%demo.local%'; -- 0
SELECT COUNT(*) FROM dim_product WHERE match_strategy = 'seed';              -- 0
SELECT COUNT(*) FROM etl_run WHERE run_key LIKE 'seed-%';                   -- 0

robots.txt is enforced below the source layer

The gate lives in the transport, not in the adapter, so a new source inherits it for free. Every decision — not just the outcome — is written to ingestion_http_log.robots_rule, and the RFC 9309 fallbacks are implemented exactly:

robots.txt stateBehaviour
4xxAllow all — RFC 9309 “unavailable” fallback
401 / 403Disallow the whole host
5xx / network errorAllow, and log the failure
Path disallowedComplianceError — the request is never made

Rate limiting, in two layers

  • Token bucket — smooths the average request rate per host, with a small burst allowance.
  • Sliding window — a hard per-minute ceiling even when bursts are permitted; the slower of the two always wins.
  • Plus the Crawl-delay from robots.txt, the per-source rate_limit_per_minute declaration, the global REQUESTS_PER_SECOND (1.0) and REQUESTS_PER_MINUTE (30) settings, and any Retry-After header — honoured in both its delta-seconds and HTTP-date forms.
  • Five consecutive failures against a host trip the circuit breaker: zero further network I/O for the rest of the run, and the skip is logged.
  • The crawler identifies itself honestly — ProductIntelligenceBot/1.12 with a real contact address.

The audit trail: one row per outbound request

This is what turns “we respected robots.txt” into a checkable statement rather than a claim. Each column in ingestion_http_log proves one thing:

  • source_code, run_id, url — which adapter asked for what, in which run
  • method, status_code, duration_ms, bytes — what it cost
  • robots_rule — which rule allowed it: robots.txt:allow, robots.txt:disallow, robots-unavailable:fallback-allow, cache, revalidated
  • from_cache, retries, user_agent — whether the network was touched at all

The live run recorded in docs/33_data_trust_and_compliance.md produced exactly this distribution:

robots_ruleRequests
robots.txt:allow2,152
cache471
robots-unavailable:fallback-allow390
robots.txt:disallow93
revalidated51

The 93 disallow rows are requests that were never made: the transport refused them before a socket was opened, and the source degraded to a warning, never to a failed run.

The purge sweep — classification is a promise, the purge is the receipt

When a source's trust level is lowered, the rows it already wrote are still in the warehouse. purge-untrusted removes them and reports exactly what it removed, in foreign-key order: source-scoped rows (staging, facts, changes) first, then the products that no longer have any observation, then the runs that no longer reference anything. The dim_source row is kept — it is the record of why the data was removed — but the source is disabled, so no future automatic run picks it up.

python -m app.cli.main purge-untrusted --dry-run   # report only
python -m app.cli.main purge-untrusted           # delete and report

Data quality & compliance

Trust is engineered, not assumed

12 rules, 6 dimensions

Completeness, validity, consistency, uniqueness, timeliness and accuracy. Each rule records an observed value, an expectation, a pass rate and a human-readable message.

Compliance by construction

robots.txt is parsed and honoured per request, sources are terms-allow-listed, rate limits and crawl delays are enforced, and every outbound call is written to an HTTP audit log.

Scored and gated

Each run produces a 0–100 quality score. Only critical failures stop the Airflow DAG, so a single anomalous rule never silently blocks the pipeline.

222 documented operations, two query surfaces

FastAPI with OpenAPI 3.1, consistent error envelopes, pagination, facets, GZip, request timing headers, rate limiting, JWT rotation, API keys and three-role RBAC.

FAQ

Asked in every review

Full answers with SQL in docs/23_glossary_and_faq.md.

Does it actually respect robots.txt?

Yes — and the evidence is queryable. Every attempt, including blocked ones, lands in ingestion_http_log. A row with robots_allowed = false and no status code is a request the crawler declined to make. The Audit screen shows the same data.

What happens if a source fails?

The run continues as partial with a warning. Five consecutive host failures trip the circuit breaker (zero further network I/O). Open Library's old /search.json path was refused this way — the source now uses the allowed /subjects feed instead.

Can I re-run a pipeline safely?

Yes. Dimensions merge on natural keys, staging is per-run, facts are keyed by grain and DQ verdicts by (run_id, rule_id). Re-running merges, never duplicates.

Is the Query Lab safe?

Yes. Only SELECT, WITH and EXPLAIN over the 23 analytical views; writes and multi-statements are rejected before execution, rows are capped.

Which sources does an automatic run collect?

Twenty of the thirty-four registered adapters. A run that is not told what to collect selects only sources that are enabled, terms-allow-listed and declared real. stooq_quotes is real but its terms forbid automated use, so it is never contacted; the eleven synthetic and two sandbox sources must be named by code.

What happens if robots.txt forbids a URL?

The request is never made. The transport raises ComplianceError before a socket is opened, and the attempt is still written to ingestion_http_log with robots.txt:disallow and no status code. The source degrades to a warning and the run finishes as partial.

How are duplicate products detected?

In three stages: an exact fingerprint match, then normalised-name equality, then a blended fuzzy score over four signals — Jaro-Winkler, token-set, trigram and digit signature. Above the 0.90 threshold the products merge, the survivor is the one with more observations, and the decision is persisted as match_strategy and match_score so it stays auditable.

Is the FX rate live?

Yes. Before every run the rates are refreshed from a key-less provider (open.er-api.com, with frankfurter.dev as the fallback) and written to dim_currency with their source and as-of date. If the providers are unreachable the last known table is used and the run continues. Every snapshot stores the rate it used, so history cannot be silently restated later.

Can I run it without Docker?

Yes. make install && make serve plus make frontend-dev runs the API on :8000 and the dashboard on :5173 straight from the host; SQLite is enough for the test suite. Docker is the six-service option, not a requirement.

How do I remove rows that came from a mock API?

python -m app.cli.main purge-untrusted. Run it with --dry-run first to see the report. It deletes staging, fact and change rows for every source below real, then the products left without an observation, then the runs left without a reference — and it reports the rows removed per table.

How do I add a new source?

Six steps, and you write no HTTP, robots, retry or rate-limit code: subclass ProductSource, declare the compliance metadata as class variables, implement fetch(limit) as a generator, decorate with @register_source, add a seed row to dim_source, and add a test. The gate lives in the transport, so the new adapter inherits the whole compliance layer for free.

Why two databases?

Because the brief requires it, and because it is a genuine portability test rather than a formality. The same model must load identically on PostgreSQL 16 and MySQL 8.4, which constrains the schema: no JSONB, no DISTINCT ON, portable boolean and timestamp handling. make verify-dialects proves there is no structural drift.
